## Real-World PDF Definition

### Synthetic PDF

A synthetic PDF is a rent roll PDF generated programmatically for testing purposes.

- Generated by `samples/create_sample_pdfs.py` or an equivalent script using reportlab or similar libraries.
- Contains fabricated data only — no real property names, tenant names, or addresses.
- Safe to commit to the public repository.
- Useful for regression testing and reproducible CI runs.
- **Does not substitute for real-world evaluation.** Synthetic samples cannot reveal layout variation, encoding quirks, or format diversity found in actual business documents.

### Real-World PDF

A real-world PDF is a text-based rent roll PDF originating from actual business operations or a third-party document that closely resembles an operational rent roll.

- Exported or printed from a property management system, Excel/Calc, or a landlord-provided document.
- Or produced by a third party in a format that represents a realistic operational rent roll.
- Must be text-based and machine-readable by pdfplumber (not scanned or image-only).
- Handled only under `samples/private/` or another gitignored location.
- **Must not be committed to the public repository.**

The following must never appear in committed files:
- The PDF file itself
- Property name, building name, company name
- Tenant names, owner names, or any personal names
- Addresses or room-level location data
- Room numbers if they can identify specific individuals
- Any other PII or sensitive business data

Only sanitized findings are committed: sample IDs, aggregate extraction metrics, recommended actions, and pattern observations without identifying details.

### Out-of-Scope PDF Types

The following PDF types are out of scope for v0.4.0 and must not be evaluated as qualifying real-world samples:

| Type | Reason |
|------|--------|
| Scanned PDFs | Require OCR; not implemented |
| Image-only PDFs | pdfplumber cannot extract tables |
| PDFs requiring vendor-specific heuristics | Not implemented without repeated evidence |
| PDFs with complex merged cells | Not supported |
| PDFs requiring multi-page table stitching | Not supported |

If no qualifying real-world PDF is available, Issue #21 remains open with no action required. No implementation work proceeds in the waiting state. This report is updated only when new samples become available.

## Patterns Observed

- **header alias gaps**: None observed in evaluated samples. All 6 canonical fields (area, cam, rent, room, status, use) were recognized across all 3 samples.
- **rent format issues**: None observed. Monthly rent fields were numeric and parseable in all samples.
- **sub-header patterns**: Observed in sample-private-003. Floor zone sub-headers (【1F区画】, 【2F区画】) were correctly detected and excluded by existing logic.
- **repeated header patterns**: Not observed in evaluated samples.
- **layout problems**: None observed. All samples use simple single-table layouts.
- **safe failure adequacy**: Not triggered in any sample. All 3 succeeded (exit 0). Safe failure behavior was not directly tested with failing samples in this evaluation.
- **diagnostics usability**: High. `--dry-run` output clearly shows input type, recognized fields, unit count, and any exclusion notes. Useful for quick validation without generating output artifacts.
- **extraction_log.json optional field gaps**: Some fields (`input_type`, `column_map`, `missing_cells_count`) are null in the PDF path. Not blocking, but worth noting for a potential narrow future issue.
